Distributed Rate Limiting

API sınırını tüm instance’lar arasında ortak hale getirin; login abuse ve 429 davranışını tasarlayın.

Mevcut projeden doğrulandı: Program.cs rate limiter kaydı (middleware pasif)

A · Gerçek hayat problemi

Her instance kendi sayacını tutarsa istemci N instance’a dağıtılan toplamda N kat limite ulaşabilir. Yalnız uygulama belleği süreç yeniden başlayınca sıfırlanır. Login brute force aynı zamanda kullanıcı varlığını 404/401 ayrımıyla öğrenmeye elverişlidir. Ortak Redis atomik sayaç sunar; proxy arkasındaki IP ancak proxy güveni doğru yapılandırılmışsa kullanılmalıdır.

B · Bu uygulamada neden?

Mevcut: Program.cs AddRateLimiter içinde fixed window, PermitLimit=1, Window=1s, QueueLimit=0 ve partition User.Identity.Name veya Host. Ancak app.UseRateLimiter() yorum satırında; çalışan rate limit yok. Built-in limiter süreç içidir, Redis destekli paylaşımlı sayaç değildir. Login hedefi gerçek POST api/auth/login. SQLite her hit için sayılmamalı; SQLite tek dosyalı kullanımda çok instance yazma için zaten sınırlıdır. Redis sayacı uygulama limit kararını koordine eder ama kimlik doğrulama/DB erişimini engellemeyi tek başına sağlamaz.

C · Özellik, key ve endpoint’ler

INCR + TTL

Fixed-window sayaç; bir Lua script içinde ilk artış ve PEXPIRE atomik yapılır. Ayrı INCR ardından EXPIRE olursa süreç arada düşüp süresiz key bırakabilir.

Sliding window

Sorted Set zaman damgalarıyla daha düzgün dağılım; daha çok bellek/komut ve trim maliyeti. Sınırın iş ihtiyacına göre seç.

Yerleşik ASP.NET limiter

Tek instance için uygundur; Redis sayaçlarına doğal olarak çevrilmez. Authentication sonrası middleware yerleşimi gerekir.

KeyTip / örnekTTL / kapsam
rate:user:{userId}:loginString sayaç; identity bazlı abuse limitPencere; username/e-posta yerine hashlenmiş identifier veya userId; anonim login öncesi userId olmayabilir.
rate:ip:{ip}:loginString sayaçPencere; IP PII kabul edilerek kısa tutulur; trusted proxy değerlendirilir.

Önerilen rotalar: POST api/auth/login (mevcut), POST api/auth/register (mevcut), GET api/product (mevcut). Login: 200 token; 401 genel hata; 429 {"error":"too_many_requests"} + Retry-After. Register: 201/400/429. Product: JWT Product rolü gerekli; 200/401/403/429. Redis counter hit operation; SQLite credentials/products remain authoritative. Login user missing currently 404 vs wrong password 401; recommended uniform 401 response to reduce enumeration.

4. Redis key yardımcısı

Dosya yolu: RestApi/Services/RateLimitRedisKeys.cs · Önerilen geliştirme

using System;
using System.Linq;

namespace RestApi.Services;

public static class RateLimitRedisKeys
{
    public static string UserWindow(int userId, string operation, long windowNumber)
    {
        if (userId <= 0) throw new ArgumentOutOfRangeException(nameof(userId));
        if (string.IsNullOrWhiteSpace(operation)
            || operation.Any(c => !char.IsAsciiLetterOrDigit(c) && c != '-'))
            throw new ArgumentException("Invalid operation key.", nameof(operation));
        return $"rate:user:{userId}:{operation}:{windowNumber}";
    }
}

Bu adımda sık yapılan hata: E-posta/Username’i Redis key’ine açık koymak; key’lerde kişisel veri yerine userId kullanın.

Dosya yolu: RestApi/Services/RateLimitService.cs · Önerilen geliştirme

using System;
using System.Linq;
using System.Threading.Tasks;
using RestApi.Models.Dto;
using StackExchange.Redis;

namespace RestApi.Services;

public sealed class RateLimitService(IConnectionMultiplexer multiplexer)
    : IRateLimitService
{
    private const string IncrementScript = @"
local count = redis.call('INCR', KEYS[1])
if count == 1 then redis.call('PEXPIRE', KEYS[1], ARGV[1]) end
return {count, redis.call('PTTL', KEYS[1])}";

    public async Task<RateLimitResultDto> CheckAsync(
        int userId, string operation, long limit, TimeSpan window)
    {
        if (limit <= 0) throw new ArgumentOutOfRangeException(nameof(limit));
        if (window <= TimeSpan.Zero) throw new ArgumentOutOfRangeException(nameof(window));

        var windowMs = checked((long)Math.Ceiling(window.TotalMilliseconds));
        if (windowMs <= 0) throw new ArgumentOutOfRangeException(nameof(window));
        var windowNumber = DateTimeOffset.UtcNow.ToUnixTimeMilliseconds() / windowMs;
        var key = (RedisKey)RateLimitRedisKeys.UserWindow(
            userId, operation, windowNumber);
        var result = (RedisResult[])await multiplexer.GetDatabase()
            .ScriptEvaluateAsync(IncrementScript,
                new[] { key }, new RedisValue[] { windowMs });
        var count = (long)result[0];
        var ttlMs = (long)result[1];
        var retrySeconds = Math.Max(1L, (ttlMs + 999) / 1000);

        return new RateLimitResultDto(
            count <= limit,
            limit,
            Math.Max(0, limit - count),
            count <= limit ? 0 : retrySeconds);
    }
}

Lua, INCR ile ilk PEXPIRE işlemini aynı Redis çalıştırımında yapar; script yalnız Redis tarafında atomiktir. Connection/timeout hatası yutulmaz; controller 503 verir (bu örneğin fail-closed seçimi). Üretimde IP/anonymized-login ve account bazlı ayrı sayaçlar gerekir.

Bu adımda sık yapılan hata: INCR ve EXPIRE’ı ayrı çağrılarda yapıp süreç iki komut arasında durursa TTL’siz sayaç bırakmak. Ayrıca bu fixed window sınırında burst olabilir; sliding window farklı bellek/işlem maliyeti getirir.

7. Controller

Dosya yolu: RestApi/Controllers/RateLimitController.cs · Önerilen geliştirme

using System.Security.Claims;
using Microsoft.AspNetCore.Authorization;
using Microsoft.AspNetCore.Mvc;
using RestApi.Services;
using StackExchange.Redis;

namespace RestApi.Controllers;

[ApiController]
[Route("api/limits")]
[Authorize]
public sealed class RateLimitController(IRateLimitService limiter) : ControllerBase
{
    [HttpPost("check")]
    public async Task<IActionResult> Check()
    {
        if (!int.TryParse(User.FindFirstValue(ClaimTypes.NameIdentifier), out var userId)
            || userId <= 0)
            return Unauthorized();

        try
        {
            var result = await limiter.CheckAsync(
                userId, "demo", 5, TimeSpan.FromMinutes(1));
            Response.Headers["Retry-After"] = result.RetryAfterSeconds.ToString();
            return result.Allowed
                ? Ok(result)
                : StatusCode(429, result);
        }
        catch (RedisException)
        {
            return StatusCode(503, new ProblemDetails
            {
                Status = 503, Title = "Rate-limit store unavailable."
            });
        }
    }
}

POST api/limits/check authenticated kullanıcı için 5/dakika demo limiti döndürür; izin varsa 200, limit dolduysa 429 + Retry-After, Redis kapalıysa 503, token/claim yoksa 401. Bu route login limiter’ı değildir; mevcut POST api/auth/login için anonim IP + normalized identifier kontrolü AuthController’a ayrıca entegre edilmelidir. Anonim login’de userId claim henüz yoktur. Mevcut 404/401 ayrımı da kullanıcı enumeration riski taşır.

Bu adımda sık yapılan hata: Login endpoint’ini kullanıcı kimliğiyle partition etmek; başarısız login öncesinde doğrulanmış user claim yoktur. Username’i raw key yapmak yerine normalize edip gizlilik için ayrı, kısıtlı bir strateji tasarlayın.

9. Son kontrol

Bu adımda sık yapılan hata: Final doğrulamayı atlayıp yalnızca başarılı HTTP yanıtına güvenmek; kalıcı DB state’i, Redis key’i ve hata senaryosunu birlikte kontrol edin.

D · Adım adım uygulama

  1. Etkinleştirme: mevcut built-in limiter’a OnRejected 429+Retry-After ekle ve authentication’dan sonra UseRateLimiter konumlandır. Doğrula: limiter route’a uygulanır; identity adı doğru partition olur. Hata: auth öncesi user-based partition.
  2. Dağıtık sayaç: RateLimitService Services’e; DI’de scoped; singleton multiplexer enjeksiyonu. Doğrula: iki API instance aynı Redis’e bağlanınca ortak limit. Hata: instance başına local sayaç.
  3. Atomik pencereler: INCR+TTL Lua ile tek Redis işlem akışında; reset zamanı ve Retry-After’ı birlikte dön. Doğrula: eşzamanlı isteklerde limit aşılmaz. Redis Lua SQLite transaction değildir.
  4. Login koruması: IP + normalized identifier ayrı sınırlar, account lockout riski, 401 eşdeğer yanıt. Doğrula: kayıtlı olmayan/kötü parolalı cevapların ayrışmaması.

E · Akış, senaryolar, riskler

HTTP → ErrorHandlerMiddleware → GlobalMiddleware → Authentication → Authorization → Rate limiter (önerilen, auth sonrası) → Controller → Redis sayaç → gerekirse SQLite
Başarılı: Sayaç pencere içinde izinli → endpoint işlenir; aşımda 429 ve doğru Retry-After.
Hatalı: Redis timeout → güvenlik endpoint’inde fail-closed (503/429 politika) ya da belgeli fallback; sessizce limitsiz devam etme. Açık fail-open SQLite/API’yi aşırı yükleyebilir.
  • Fixed window sınırında kısa süreli burst olabilir; sliding window maliyetini karşılaştır.
  • Anonymous User.Identity.Name boş olabilir; shared Host key tüm ziyaretçileri tek partition’a toplar.
  • Key’e raw email koyma; hashed normalized identifier gerekiyorsa secret/key rotation planla.
  • Redis memory/eviction sayaçları düşürüp limiti gevşetebilir. SQLite kalıcı kullanıcı kaynağıdır, dağıtık limiter değildir.

F · Öğrenme çıktıları ve önkoşul

INCR/PEXPIRE atomikliği, fixed/sliding window, local/distributed farkı, partitioning ve HTTP 429 öğrenilir. Önkoşul yok; Modül 03’te benzer fail policy düşünülür.

G · Görevler

  1. Bir dakikalık fixed window simüle et.
    İpucuKey ve pencereyi endpoint/user sınırına göre ayır.
  2. Login için IP ve identifier limitlerini tasarla.
    İpucuAuthentication öncesi user id mevcut değildir; identifier’ı key’e açık yazma.
  3. INCR/EXPIRE crash yarışını test et, sonra Lua ile kapat.
    İpucuScript’te ilk artışta PEXPIRE; testte paralel yük ve TTL gözlemi.

H · Production checklist / kendini değerlendir

Kendini değerlendir · yanıtları göster

1) Yerleşik limiter neden distributed değil? In-process state. 2) INCR ardından EXPIRE riski? Aradaki crash süresiz key bırakabilir. 3) User identity ne zaman kullanılabilir? Authentication sonrasında. 4) 429 ne sunmalı? Retry-After, doğru reset zamanı.

Sık yapılan hatalar

  • UseRateLimiter’ı authentication öncesi koymak → authenticated partition için sonrasına al.
  • EXPIRE’ı her istekte resetlemek → pencereyi kayan şekilde uzatabilir; yalnız ilk sayımda atomik TTL.
  • Redis down iken fail-open varsaymak → endpoint riskine göre fail policy belirle.
