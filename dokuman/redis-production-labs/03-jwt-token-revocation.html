JWT Token Revocation

Logout sonrası stateless access token’ı nasıl reddederiz; merkezi kontrolün maliyetini ve güvenlik kararını tartışın.

Mevcut projeden doğrulandı: AuthController.Login · Program.cs · ErrorHandlerMiddleware

A · Gerçek hayat problemi

JWT imzası ve süresi geçerli kaldıkça logout tek başına token’ı geçersiz kılmaz. Çalınan token süresi dolana kadar kullanılabilir. Bir instance’ın belleğindeki denylist diğer instance’a yayılmaz; restart’ta kaybolur. Redis’e JTI denylist eklemek her istekte merkezi erişim getirir.

B · Bu uygulamada Redis neden?

AuthController.Login 1 saatlik HmacSha256Signature token oluşturur; claims NameIdentifier, Name ve role’dur; JTI yok. Program.cs issuer/audience validasyonunu kapatmış, signing key doğrulaması açık; token ömrü TokenValidationParameters varsayılan lifetime kontrolüne dayanır. Logout ve revocation endpoint’i yok. Redis String + TTL geçici denylist sağlar; SQLite token oturum tablosu da alternatiftir ancak sorgu/temizlik ister. Redis kaydı eviction veya veri kaybıyla düşebilir ve tek başına mutlak iptal garantisi değildir. Fail-closed erişilebilirliği azaltır; fail-open iptal kontrolünü devre dışı bırakır. Karar endpoint riskine göre açıkça yazılmalı.

C · Özellikler ve key tasarımı

JTI + String key

Her token’a rastgele benzersiz jti ekle; denylist’te yalnız o tanımlayıcıyı sakla, token’ın kendisini değil.

TTL = kalan ömür

Exp-now kadar TTL ile geçersiz token kaydı doğal olarak temizlenir. TTL fiziksel silinmenin kesin anı değildir.

OnTokenValidated

İmza/lifetime kontrollerinden sonra denylist kontrolü; Redis bağımlılığı her yetkili API isteğine taşınır.

Adım Adım .NET Uygulama Rehberi

Önerilen geliştirme: JTI, logout route, revocation service ve JWT event’i mevcutta yoktur. JTI eklenene kadar revoke endpoint’i çalışmayacaktır; adımları sırasıyla uygulayın.

1. Hazırlık

Mevcut projeden doğrulandı: .NET 9, JwtBearer 9.0.2, StackExchange.Redis 3.3.1, singleton multiplexer ve JWT signing key configuration key’i mevcut. Secret value’ları appsettings’e/HTML’e kopyalamayın. Redis local değilse docker compose up -d redis. Yeni paket gerekmez.

Bu adımda sık yapılan hata: `SaveToken=true` veya imza doğrulandı diye token logout sonrası iptal oluyor sanmak. JTI denylist ayrı kontrol ve her doğrulamada merkezi Redis bağımlılığı getirir.

2. Model ve veritabanı

Kalıcı token/session entity bu örnekte gerekmiyor: revocation kaydı kısa ömürlüdür ve Redis TTL’i token expiry’ye bağlanır. DbSet/table/migration yok; EF komutu çalıştırılmaz. Daha güçlü audit/kalıcı logout ihtiyacı varsa relational session store ayrıca tasarlanmalıdır; Redis tek başına kalıcılık garantisi değildir.

Bu adımda sık yapılan hata: JTI denylist’ini süresiz key olarak tutmak. Key TTL’i token’ın kalan ömrünü aşmamalıdır.

3. DTO

Logout request body’si gerekmez; token zaten Bearer header’dadır. Response da 204 No Content olduğundan yeni DTO sınıfı gerekmiyor. Bu, request’te client JTI alıp başka token iptal ettirme riskini önler.

Bu adımda sık yapılan hata: İptal edilecek JTI’yi request body’den almak. Yalnızca doğrulanmış mevcut token’ın claim’ini kullanın.

4. Redis key helper

Dosya yolu: RestApi/Services/TokenRevocationRedisKeys.cs · Önerilen geliştirme

using System;

namespace RestApi.Services;

public static class TokenRevocationRedisKeys
{
    public static string ForJti(string jti)
    {
        if (string.IsNullOrWhiteSpace(jti)
            || jti.Length > 128
            || jti.Any(char.IsControl))
            throw new ArgumentException("Invalid token identifier.", nameof(jti));
        return $"auth:revoked:{jti}";
    }
}

Bu adımda sık yapılan hata: Raw JWT’yi key’e yazmak veya loglamak. Yalnız JTI kullanın; Bearer token ve Authorization header’ını asla loglamayın.

5. Servis katmanı

using System;

}

Dosya yolu: RestApi/Services/TokenRevocationService.cs · Önerilen geliştirme

using System;
using System.Threading.Tasks;
using StackExchange.Redis;

namespace RestApi.Services;

public sealed class TokenRevocationService(IConnectionMultiplexer multiplexer)
    : ITokenRevocationService
{
    public async Task RevokeAsync(string jti, DateTime expiresUtc)
    {
        var remaining = expiresUtc - DateTime.UtcNow;
        if (remaining <= TimeSpan.Zero) return;
        await multiplexer.GetDatabase().StringSetAsync(
            TokenRevocationRedisKeys.ForJti(jti), "1", remaining);
    }

    public Task<bool> IsRevokedAsync(string jti) =>
        multiplexer.GetDatabase().KeyExistsAsync(
            TokenRevocationRedisKeys.ForJti(jti));
}

Redis exception yutulmaz. Authorization pipeline’daki caller fail-closed olarak token validation’ı reddeder; revocation key’i kalan token süresi kadar yaşar. TTL tam fiziksel silinme anı garantisi değildir.

Bu adımda sık yapılan hata: Redis timeout’unda false (not revoked) dönmek. Bu, erişilemeyen güvenlik kontrolünü sessizce devre dışı bırakır.

Dosya yolu: RestApi/Program.cs (mevcut AddJwtBearer options bloğunun içine) · Önerilen geliştirme

options.MapInboundClaims = false;
options.Events = new JwtBearerEvents
{
    OnTokenValidated = async context =>
    {
        var jti = context.Principal?.FindFirst(
            System.IdentityModel.Tokens.Jwt.JwtRegisteredClaimNames.Jti)?.Value;
        if (string.IsNullOrWhiteSpace(jti))
        {
            context.Fail("Required token identifier is missing.");
            return;
        }

        var service = context.HttpContext.RequestServices
            .GetRequiredService<ITokenRevocationService>();
        try
        {
            if (await service.IsRevokedAsync(jti))
                context.Fail("Token has been revoked.");
        }
        catch (StackExchange.Redis.RedisException)
        {
            // Fail closed: authentication fails; never skip the check.
            context.Fail("Token revocation service is unavailable.");
        }
    }
};

`MapInboundClaims = false` keeps registered jti/exp names predictable; NameIdentifier/Name/Role claims are emitted as ClaimTypes URI claims and remain available. Enabling this event also rejects older valid tokens without JTI: deploy JTI-producing login first, allow old tokens to expire, then enforce revocation. Existing Authentication → Authorization order remains; no middleware is added. Redis outage fails closed (usually 401); separate 503 requires authentication failure response customization.

Bu adımda sık yapılan hata: `OnTokenValidated` event’i kurup exception’ı yutmak. Güvenlik açısından sessiz bypass yok; fail-closed availability maliyetini kabul edin ve gözlemleyin.

7. Auth token claim’i ve logout controller

Dosya yolu: RestApi/Controllers/AuthController.cs (SecurityTokenDescriptor.Subject içine claim ekle) · Önerilen geliştirme

new Claim(
    System.IdentityModel.Tokens.Jwt.JwtRegisteredClaimNames.Jti,
    Guid.NewGuid().ToString("N"))

Bunu mevcut Subject claim array’ine NameIdentifier ve Name yanında ekleyin; yeni token’larda jti olur. Eski, jti’siz token’lar revoke akışına geçmeden önce expire olmalı veya kontrollü şekilde reddedilmelidir.

Dosya yolu: RestApi/Controllers/LogoutController.cs · Önerilen geliştirme

using System.Globalization;
using System.IdentityModel.Tokens.Jwt;
    using System.Security.Claims;
using Microsoft.AspNetCore.Authorization;
using Microsoft.AspNetCore.Mvc;
using RestApi.Services;
using StackExchange.Redis;

namespace RestApi.Controllers;

[ApiController]
[Route("api/auth")]
[Authorize]
public sealed class LogoutController(ITokenRevocationService revocations)
    : ControllerBase
{
    [HttpPost("logout")]
    public async Task<IActionResult> Logout()
    {
        if (!int.TryParse(User.FindFirstValue(ClaimTypes.NameIdentifier), out var userId)
            || userId <= 0)
            return Unauthorized();
        var jti = User.FindFirst(JwtRegisteredClaimNames.Jti)?.Value;
        var exp = User.FindFirst(JwtRegisteredClaimNames.Exp)?.Value;
        if (string.IsNullOrWhiteSpace(jti)
            || !long.TryParse(exp, NumberStyles.Integer,
                CultureInfo.InvariantCulture, out var seconds))
            return Unauthorized();

        try
        {
            await revocations.RevokeAsync(
                jti, DateTimeOffset.FromUnixTimeSeconds(seconds).UtcDateTime);
            return NoContent();
        }
        catch (RedisException)
        {
            return StatusCode(503, new ProblemDetails
            {
                Status = 503, Title = "Token revocation store unavailable."
            });
        }
    }
}

Logout 204; token/JTI/exp eksikse 401; Redis write hatası 503. Rol eklenmiyor; yalnız authenticated caller kendi bearer token’ını revoke eder.

Bu adımda sık yapılan hata: Logout rotasını AllowAnonymous yapmak ya da body’deki başka kullanıcının token’ını iptal etmek. Yalnız valid JWT principal’ı ve onun JTI claim’i kullanılmalıdır.

9. Son kontrol

Bu adımda sık yapılan hata: Final doğrulamayı atlayıp yalnızca başarılı HTTP yanıtına güvenmek; kalıcı DB state’i, Redis key’i ve hata senaryosunu birlikte kontrol edin.

E · Adım adım ve .NET örneği

  1. JTI üret: SecurityTokenDescriptor.Subject’e Jti claim ekle (önerilen); doğrula, iki token JTI’ları ayrık. JTI mevcut değil.
  2. Logout: JWT’yi validate edip exp/jti oku; key TTL’ini kalan ömürden hesapla, non-positive ise yazma. Her token için kayıt.
  3. Doğrulama: AddJwtBearer OnTokenValidated içinde Redis sorgula; revoked olursa context.Fail. Redis exception için AuthenticationFailed event + kontrollü 503/error response; sessizce atlama.
  4. Gözlem: Header/token redaction; mevcut logger bütün header’ları yazar ve login parola türevlerini console’a çıkarır. Kod değiştirme bu eğitim kapsamı dışı.

F · İstek akışı, production kararları

HTTP → ErrorHandlerMiddleware (mevcut header log riski) → GlobalMiddleware → Authentication (imza/lifetime + önerilen Redis JTI kontrolü) → Authorization (Product/Note) → Controller → SQLite/Redis
Başarılı: imza/lifetime doğru, JTI denylist’te değil → authorization → controller.
Başarısız: revoked → authentication fail/401. Redis erişilemiyor → güvenlik açısından sessiz geçiş yok; belgeli 503 fail-closed veya sınırlı acil durum policy.
  • Revocation kontrolü stateless doğrulamaya merkezi gecikme ve availability bağımlılığı ekler.
  • Key eviction/restart/persistence davranışı güvenlik kontrolünü zayıflatabilir; eviction policy denetlenmeli.
  • SaveToken=true ve ErrorHandlerMiddleware header döngüsüyle birlikte bearer token log’a yazılabilir; log erişimi de sır yönetimidir.
  • Issuer/audience doğrulama mevcutta kapalıdır; bu modül bunları varmış gibi sunmaz, prod’da ayrı ele alınmasını önerir.

G · Öğrenme çıktıları / önkoşul

JTI, kalan TTL, token denylist ve merkezi kontrolün ödünleşimi anlaşılır. Önkoşul Modül 02’de Redis outage policy; sonraki Modül 06 OTP’de hassas veri koruması.

H · Uygulama görevleri

  1. Token descriptor’a JTI ekle.
    İpucuJwtRegisteredClaimNames.Jti için kriptografik rastgele ID üret; mevcut kodda yok.
  2. Logout endpoint’i ile kalan ömür kadar denylist kaydı oluştur.
    İpucuExp ile UTC now farkını hesapla; negatif sürede kayıt yazma.
  3. Redis’i erişilemez yapıp protected endpoint davranışını doğrula.
    İpucuOnTokenValidated failure exception’ını sessizce yutma; fail-closed seçimi ve 503 dönüşümü tasarla.

I · Production checklist / kendini değerlendir

Kendini değerlendir · yanıtları göster

1) JWT logout neden otomatik iptal değildir? İmza/süre geçerliliği devam eder. 2) JTI neden? Tek token’ı sınırlı anahtarla ayırt etmek. 3) TTL? En fazla token’ın kalan ömrü. 4) Redis down? Fail-open kontrolü atlar; seçim belgelenmeli. 5) Revocation bedeli? Stateful merkezi bağımlılık.

Sık yapılan hatalar

  • Token’ın tamamını denylist key yapmak → yalnız JTI kullan.
  • Her kayda sabit bir saat TTL → token kalan ömrünü hesapla.
  • Redis exception’ında “not revoked” dönmek → güvenlik kararını fail policy ile açık ver.
  • Bearer header veya token’ı loglamak → redaction ve hassas veri politikası uygula.
