Background Jobs & Redis Streams

Uzun HTTP işini producer/consumer hattına ayırın; pending/ack ve retry’ı doğru yönetin.

Önerilen geliştirme · BackgroundService/worker mevcut değil

A · Problem / B · Redis rolü

Rapor, toplu bildirim veya cache warm-up HTTP isteğinde çalışırsa latency/timeouts artar; client retry duplicate side effect üretebilir. In-memory queue process restart’ta kaybolur. Redis Stream kayıtlı event, consumer group dağıtımı ve pending entry takibi sağlar. List basit FIFO pop’dur; visibility/consumer ownership yönetimi kendin gerekir. Stream’in retention/persistence ve failover garantileri deployment’a bağlı; exactly-once delivery yoktur. SQLite job table is durable option; database/Redis cross-transaction/outbox tasarlanmalı. Product cache refresh gerçek örnek; worker mevcut değil. SQLite tek dosya multi-instance writes için sınırlı.

C · Stream özellikleri

XADD: event append, generated ID.
Consumer group: XREADGROUP partitioned work.
Pending + XACK: worker aldı ama ack etmedi; claim/retry/recovery gerekir.
Dead-letter: retry limit sonrası ayrı stream/kalıcı tablo; error detail sanitize.
KeyTipRetention / scope
jobs:stream:maintenanceStream: taskId/type/payloadShared worker queue; maxlen/trim policy, pending tracking and durable DB job record when needed. TTL usually not used for entire stream key.
jobs:status:{jobId}Hash status / attemptsTTL aligned to UX retention; job history authoritative SQLite if required.

E · Uygulama adımları

  1. Define typed event and idempotency/job ID; API returns 202 quickly.
  2. Add Stream consumer group and worker as BackgroundService; for scoped ApplicationDbContext use IServiceScopeFactory per message (DbContext is scoped). Multiplexer remains singleton.
  3. Process then persist result, XACK after successful durable effect; if crash between effect and ack, same event may run again—handler idempotency required.
  4. Implement pending claim/retry/backoff/dead-letter, poison message alert, retention and graceful cancellation. Consider broker if routing/delivery/operations outgrow Redis Streams.

Dosya yolu: RestApi/Services/RedisJobQueue.cs · Önerilen geliştirme

using System.Threading;
using System.Threading.Tasks;
using RestApi.Models.Dto;
using StackExchange.Redis;
namespace RestApi.Services;
public sealed class RedisJobQueue(IConnectionMultiplexer multiplexer) : IJobQueue
{
    private readonly IDatabase _db = multiplexer.GetDatabase();
    public async Task<string> EnqueueAsync(int userId, QueueJobDto job, CancellationToken ct)
    {
        ct.ThrowIfCancellationRequested();
        var id = await _db.StreamAddAsync(JobStreamKeys.Stream, new[]
        {
            new NameValueEntry("ownerId", userId),
            new NameValueEntry("type", job.Type),
            new NameValueEntry("payload", job.Payload)
        });
        return id.ToString();
    }
}

Dosya yolu: RestApi/Services/JobStreamWorker.cs · Önerilen geliştirme

using System;
using System.Linq;
using System.Threading;
using System.Threading.Tasks;
using Microsoft.Extensions.Hosting;
using Microsoft.Extensions.Logging;
using StackExchange.Redis;
namespace RestApi.Services;
public sealed class JobStreamWorker(
    IConnectionMultiplexer multiplexer, ILogger<JobStreamWorker> logger)
    : BackgroundService
{
    private readonly IDatabase _db = multiplexer.GetDatabase();
    private readonly string _consumer = $"{Environment.MachineName}-{Guid.NewGuid():N}";

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        var groupReady = false;
        while (!stoppingToken.IsCancellationRequested)
        {
            try
            {
                if (!groupReady)
                {
                    try
                    {
                        await _db.StreamCreateConsumerGroupAsync(
                            JobStreamKeys.Stream, JobStreamKeys.Group, "0-0", true);
                    }
                    catch (RedisServerException ex) when (ex.Message.Contains("BUSYGROUP")) { }
                    groupReady = true;
                }

                var entries = await _db.StreamReadGroupAsync(
                    JobStreamKeys.Stream, JobStreamKeys.Group, _consumer, ">", 10);
                foreach (var entry in entries)
                {
                    stoppingToken.ThrowIfCancellationRequested();
                    var type = entry.Values.FirstOrDefault(v => v.Name == "type").Value;
                    var payload = entry.Values.FirstOrDefault(v => v.Name == "payload").Value;
                    if (type == "echo")
                    {
                        logger.LogInformation("Processed demo job {JobId}; payload length {PayloadLength}",
                            entry.Id, payload.ToString().Length);
                        await _db.StreamAcknowledgeAsync(
                            JobStreamKeys.Stream, JobStreamKeys.Group, entry.Id);
                    }
                    else logger.LogError("Unsupported job type {JobType}, message {JobId} left pending",
                        type.ToString(), entry.Id);
                }
                if (entries.Length == 0)
                    await Task.Delay(TimeSpan.FromSeconds(1), stoppingToken);
            }
            catch (RedisException ex)
            {
                groupReady = false;
                logger.LogError(ex, "Redis stream unavailable; worker will retry.");
                await Task.Delay(TimeSpan.FromSeconds(2), stoppingToken);
            }
        }
    }
}

Unknown types remain pending; production must add XAUTOCLAIM, retry limits, dead-letter handling and alerts. Worker does not persist job status or make side effects; it demonstrates group read + ack mechanics.

Bu adımda sık yapılan hata: Exception’ı sessizce yutup worker’ı sağlıklı göstermek. This worker logs outage and retries; monitor pending count.

7. Controller

Dosya yolu: RestApi/Controllers/JobsController.cs · Önerilen geliştirme

using System.Security.Claims;
using Microsoft.AspNetCore.Authorization;
using Microsoft.AspNetCore.Mvc;
using RestApi.Models.Dto;
using RestApi.Services;
using StackExchange.Redis;
namespace RestApi.Controllers;
[ApiController]
[Route("api/jobs")]
[Authorize]
public sealed class JobsController(IJobQueue queue) : ControllerBase
{
    [HttpPost]
    public async Task<IActionResult> Enqueue(QueueJobDto request, CancellationToken ct)
    {
        if (!int.TryParse(User.FindFirstValue(ClaimTypes.NameIdentifier), out var userId)
            || userId <= 0) return Unauthorized();
        try { return Accepted(new { id = await queue.EnqueueAsync(userId, request, ct), status = "queued" }); }
        catch (RedisException) { return StatusCode(503); }
    }
}

POST 202 means queued, invalid DTO 400, anonymous 401, Redis failure 503. No completion/status endpoint is claimed.

Bu adımda sık yapılan hata: 202 Accepted’i business operation completed gibi sunmak.

.NET worker shape

public sealed class MaintenanceWorker(
    IConnectionMultiplexer mux, IServiceScopeFactory scopeFactory)
    : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            // Read one message from the consumer group first.
            await using var scope = scopeFactory.CreateAsyncScope();
            var db = scope.ServiceProvider.GetRequiredService<ApplicationDbContext>();
            var redis = mux.GetDatabase();
            // Process idempotently with this message-scoped DbContext,
            // then acknowledge only after durable work succeeds.
            await Task.Delay(TimeSpan.FromSeconds(1), stoppingToken);
        }
    }
}

This skeleton shows lifetimes only; blocking read loop, pending reclaim, cancellation and error handling still required. BackgroundService is proposed, not current.

F · Akış ve production

HTTP → ErrorHandlerMiddleware → GlobalMiddleware → Authentication → Authorization → JobController → XADD → BackgroundService → IServiceScopeFactory → SQLite/Redis → XACK
Success: accepted event → worker reads → idempotent DB/cache operation → ack.
Failure: worker crashes after DB commit but before ack → pending reclaim and duplicate safe processing.
  • Consumer group pending entries need monitoring and reclaim. Stuck worker recovery.
  • Redis Streams persistence is deployment-dependent; AOF in compose is configured, but not a substitute for backups/delivery SLA.
  • Trim can remove entries workers still need; use carefully.
  • Redis+SQLite is not distributed transaction. Transactional outbox or reconciliation for DB-originated events.
  • Exactly-once not supplied by Streams alone. For advanced routing, long retention or managed guarantees, use a dedicated broker.

Outcomes: producer/consumer, ack, pending, retry, idempotent worker. Prerequisite Mod 09 idempotency recommended.
