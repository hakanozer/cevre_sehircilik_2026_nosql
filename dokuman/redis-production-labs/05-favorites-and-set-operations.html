Favorites & Set Operations

Ürün favorilerini idempotent küme işlemleriyle yönetin ve cache ile kalıcı ilişkiyi ayırın.

Önerilen geliştirme · Favori entity/API yok

A · Problem / B · Neden Redis?

Favori butonuna tekrarlı tıklama duplicate satır üretmemeli. Uygulama belleği instance değişiminde farklı görünüm verir; her profil açılışında SQLite sorgusu maliyetlidir. Redis Set’te SADD aynı üye için tekrarda duplicate oluşturmaz, SISMEMBER membership kontrolü ve SINTER ortak beğeniler sağlar. SQLite unique (UserId, ProductId) index’i kalıcı son savunmadır. Redis Set tek başına kalıcı doğruluk değildir; cache miss/invalidation ve evictions düşünülmelidir. Çok büyük kümelerde memory/membership maliyeti ölçülür. SQLite multi-instance write sınırı vardır.

C · Özellikler + key

SADD / SREM: favori ekle/kaldır; tekrar add güvenlidir.
SISMEMBER: kullanıcı bu ürünü favoriledi mi.
SINTER: iki kullanıcının ortak ürünleri; büyük kümelerde pahalı olabilir.
KeyTip / örnekTTL / kullanıcı ayrımı / not
favorite:user:{userId}:productsSet productId strings {"12","19"}Cache ise DB’den yeniden kurulabilir; süre/eviction bilinçli. userId JWT claim’i, username/e-posta yok. Kalıcı unique relation SQLite.

D · Endpoint’ler

API’lerin tümü Önerilen geliştirme. Mevcut GET api/product ürünleri verir; sınıf düzeyinde Product rolü gerekir. Favori controller’a authenticated owner rule önerilir; yeni Favorite/Admin rol mevcut değildir.

1. Hazırlık

Mevcut projeden doğrulandı: .NET 9, EF Core SQLite, StackExchange.Redis 3.3.1 ve singleton multiplexer var; ek paket gerekmez. Başlat: docker compose up -d redis.

Bu adımda sık yapılan hata: Redis Set’i tek kalıcı veri kaynağı yapmak. Redis restart/eviction olursa relation’lar kaybolur; SQLite authoritative kalır.

using System;

namespace RestApi.Services;

public static class FavoriteRedisKeys
{
    public static string ForUser(int userId) =>
        userId > 0 ? $"favorite:user:{userId}:products"
                    : throw new ArgumentOutOfRangeException(nameof(userId));

Bu adımda sık yapılan hata: User name/email’i key içine koyup PII yaymak. Use numeric, claim-derived user ID.

5. Servis

Dosya yolu: RestApi/Services/IFavoriteService.cs · Önerilen geliştirme

using System.Collections.Generic;
using System.Threading;
using System.Threading.Tasks;

namespace RestApi.Services;

public interface IFavoriteService
{
    Task<IReadOnlyList<int>> GetAsync(int userId, CancellationToken ct);
    Task<bool> AddAsync(int userId, int productId, CancellationToken ct);
    Task RemoveAsync(int userId, int productId, CancellationToken ct);
}

Dosya yolu: RestApi/Services/FavoriteService.cs · Önerilen geliştirme

using System.Collections.Generic;
using System.Linq;
using System.Threading;
using System.Threading.Tasks;
using Microsoft.EntityFrameworkCore;
using RestApi.Data;
using RestApi.Models;
using StackExchange.Redis;

namespace RestApi.Services;

public sealed class FavoriteService(
    ApplicationDbContext context, IConnectionMultiplexer multiplexer)
    : IFavoriteService
{
    private readonly IDatabase _redis = multiplexer.GetDatabase();

    public async Task<IReadOnlyList<int>> GetAsync(int userId, CancellationToken ct)
    {
        var key = (RedisKey)FavoriteRedisKeys.ForUser(userId);
        var cached = await _redis.SetMembersAsync(key);
        if (cached.Length > 0)
            return cached.Select(v => int.TryParse(v.ToString(), out var id) ? id : 0)
                .Where(id => id > 0).Order().ToArray();

        var ids = await context.Favorites.AsNoTracking()
            .Where(f => f.UserId == userId).Select(f => f.ProductId).ToListAsync(ct);
        if (ids.Count > 0)
            await _redis.SetAddAsync(key, ids.Select(id => (RedisValue)id.ToString()).ToArray());
        return ids;
    }

    public async Task<bool> AddAsync(int userId, int productId, CancellationToken ct)
    {
        if (!await context.Products.AnyAsync(p => p.Id == productId, ct)) return false;
        var exists = await context.Favorites.AnyAsync(
            f => f.UserId == userId && f.ProductId == productId, ct);
        if (!exists)
        {
            context.Favorites.Add(new Favorite { UserId = userId, ProductId = productId });
            try { await context.SaveChangesAsync(ct); }
            catch (DbUpdateException)
            {
                if (!await context.Favorites.AnyAsync(
                    f => f.UserId == userId && f.ProductId == productId, ct))
                    throw;
                // A concurrent request inserted the same relation; PUT remains idempotent.
            }
        }
        await _redis.SetAddAsync(FavoriteRedisKeys.ForUser(userId), productId.ToString());
        return true;
    }

    public async Task RemoveAsync(int userId, int productId, CancellationToken ct)
    {
        var row = await context.Favorites.SingleOrDefaultAsync(
            f => f.UserId == userId && f.ProductId == productId, ct);
        if (row is not null)
        {
            context.Favorites.Remove(row);
            await context.SaveChangesAsync(ct);
        }
        await _redis.SetRemoveAsync(FavoriteRedisKeys.ForUser(userId), productId.ToString());
    }
}

Errors are not swallowed: Redis outage propagates through default error handling (500) after DB may already have committed. Cache repair is safe by invalidating the per-user key and letting GET rebuild. For production, catch RedisException in controller and return documented 503 with the “DB may have committed” caveat; do not pretend transaction rollback.

Bu adımda sık yapılan hata: Retrying after Redis error without considering persisted relation. Make PUT idempotent, preserve DB unique index and repair cache from SQLite.

7. Controller

Dosya yolu: RestApi/Controllers/FavoritesController.cs · Önerilen geliştirme

using System.Security.Claims;
using Microsoft.AspNetCore.Authorization;
using Microsoft.AspNetCore.Mvc;
using RestApi.Models.Dto;
using RestApi.Services;

namespace RestApi.Controllers;

[ApiController]
[Route("api/favorites")]
[Authorize]
public sealed class FavoritesController(IFavoriteService service) : ControllerBase
{
    private bool TryUserId(out int id) =>
        int.TryParse(User.FindFirstValue(ClaimTypes.NameIdentifier), out id) && id > 0;

    [HttpGet]
    public async Task<IActionResult> Get(CancellationToken ct)
    {
        if (!TryUserId(out var userId)) return Unauthorized();
        return Ok(new FavoritesResponseDto(await service.GetAsync(userId, ct)));
    }

    [HttpPut("{productId:int}")]
    public async Task<IActionResult> Add(int productId, CancellationToken ct)
    {
        if (!TryUserId(out var userId)) return Unauthorized();
        if (productId <= 0) return BadRequest();
        return await service.AddAsync(userId, productId, ct) ? NoContent() : NotFound();
    }

    [HttpDelete("{productId:int}")]
    public async Task<IActionResult> Remove(int productId, CancellationToken ct)
    {
        if (!TryUserId(out var userId)) return Unauthorized();
        if (productId <= 0) return BadRequest();
        await service.RemoveAsync(userId, productId, ct);
        return NoContent();
    }
}

GET 200, PUT 204 / unknown product 404, DELETE 204 including repeat, invalid ID 400, unauthenticated 401. Existing roles are Product and Note; this endpoint deliberately allows every authenticated account rather than adding an imaginary role.

Bu adımda sık yapılan hata: Yalnızca action’ı [Authorize] yapıp ownership’i service query’sinde unutmamak. Every DB operation filters with claim-derived userId.

E · Adım adım + komut laboratuvarı

  1. Add Favorite entity (UserId, ProductId) and composite unique index; migration using info.txt flow. Confirm duplicate rejected by DB even if cache stale.
  2. FavoriteService uses multiplexer singleton; Get list from cache, DB rebuild on miss. Verify two app instances see same state.
  3. Write DB then update cache; failure between steps needs invalidate/rebuild/outbox or treat cache as disposable. ProductController.Delete currently does not invalidate products:all; favorite cleanup is an additional consistency requirement.

F · Akış ve Production notları

HTTP → ErrorHandlerMiddleware → GlobalMiddleware → Authentication → Authorization → FavoriteController → SQLite relation + Redis Set read/cache
Başarılı: token claim’den userId → product exists → unique row stored → SADD → 204.
Hatalı: Redis cache key evicted → SQLite rebuild; duplicate relational insert → unique conflict handled as idempotent result.

Set memory scales with cardinality; ortak SINTER costly for large user lists. Cache invalidate on Product delete/update; SQLite relation enforces integrity. Redis offline should not silently return empty favorites when that implies data loss. TTL is not precise deletion. Learned: set algebra, idempotent adds, persistence boundary. Prerequisite none; next Module 09 covers retries.

Görevler / Checklist

  1. Tekrarlı favorileme.
    İpucuSADD + composite unique index.
  2. Ortak ürün setini göster.
    İpucuSINTER; limit user set size.
  3. Ürünü silerken Redis/SQLite favorilerini tutarlı tut.
    İpucuFK policy, event/outbox, SREM/invalidation.
Kendini değerlendir · yanıtlar

1) SADD repeat? Üye yinelenmez. 2) Kalıcı unique index neden? Redis kaybı/yarışı DB’de durdurur. 3) Product delete etkisi? Favorite relation/key stale olur; cleanup gerekir. 4) SINTER ne zaman sakıncalı? Çok büyük kümelerde CPU/memory maliyeti.

Sık yapılan hatalar

  • Redis Set’i kalıcı kayıt sanmak → SQLite relation’a yaz.
  • Yalnız Redis’te duplicate önlemek → DB unique index ekle.
  • Product delete’i unutmak → foreign key ve key/index cleanup planla.
