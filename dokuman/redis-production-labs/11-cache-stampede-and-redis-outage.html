Cache Stampede & Redis Outage

Mevcut cache-aside akışını okuyun; stale data, cold cache ve Redis kesintisine yönelik düzeltmeleri yalnızca öneri olarak tasarlayın.

Mevcut projeden doğrulandı: ProductController.GetAll, Create, Update, Delete

A · Gerçek problem / B · Projedeki davranış

Cache key aynı anda expire olunca çok sayıda request SQLite’a düşer (stampede). Cache yoksa DB’ye fallback dayanıklılığı artırabilir ama arızada DB’yi aşırı yükleyebilir. Redis erişilemezliği timeout/exception davranışını belirgin kılmalıdır.

Mevcut: ProductController.GetAll önce Redis GET products:all, miss ise SQLite AsNoTracking ToListAsync, sonra Redis SET JSON TTL 10 dakika. TTL jitter/single-flight yok. Update/Delete cache silmiyor; cache hit’te en fazla eski liste TTL bitene kadar dönebilir. Create önce KeyDelete, sonra DB Add/SaveChanges: save başarısız olursa cache yok; daha önemlisi invalidation ile DB commit arasında istek SQLite’tan eski liste okuyup cache’e geri yazabilir. Cache GET/SET çevresinde try/catch/fallback yok. Redis failure GetAll exception’ını fırlatır; ErrorHandlerMiddleware bunu yakalar, genel 500 döndürür ve exception.Message body’ye yazar; Redis exception için özel mapping yok. Program.cs SyncTimeout ve ConnectTimeout 5000ms.

Appsettings Redis configured; IConnectionMultiplexer singleton and synchronous Connect on app startup. SQLite is single-file and limited for multi-instance writes. Cache key global list, not user-specific.

C · Özellikler + key tasarımı

Cache-aside: app reads cache, then DB, populates cache. DB authoritative.
TTL jitter: expiry spread, simultaneous reload chance reduced; cache freshness window changes.
Single-flight: per-key local/in-process request coalescing; multiple instances may still stampede, distributed lock has lease tradeoff.
Stale-while-revalidate: serve bounded stale copy only if business allows; metadata needed.
KeyTip / exampleTTL / scope / notes
products:allString serialized Product listActual 10m, fixed. Global list key, currently Create deletes before save; Update/Delete do not invalidate. No data version/jitter.
products:all:v{version}Suggested String cacheTTL policy + random jitter; version/epoch invalidation proposal; not currently used.

D · Endpoint design

GET api/product, POST api/product, PUT/DELETE api/product/{id} Mevcut projeden doğrulandı; all are protected by controller-level Product role; no AllowAnonymous.

Metot/URLSample response / failureRedis / SQLite responsibility

Role Product required even GET list, although Postman Product List request has no auth token setup; this mismatch is real.

E · Improvement lab (not applied) / Redis commands

  1. Move invalidation after successful DB commit for Create/Update/Delete; however post-commit Redis failure needs an outbox/retry or version strategy.
  2. Add jitter: random extra duration within a bounded policy. Single-flight DB fetch per key in an instance; for multiple instances use careful distributed coordination or stale refresh.
  3. Map Redis timeout explicitly: cache bypass to SQLite may be appropriate for low volume, but protect SQLite with concurrency limit/circuit breaker/stale fallback; no blind fallback under load.
  4. Log structured error class/request id, redact headers and avoid exception messages with secrets. Existing ErrorHandler prints all headers; errors expose exception.Message in response.

Adım Adım .NET Uygulama Rehberi

Önerilen geliştirme: This lab adds a separate cache endpoint/service; it does not rewrite existing ProductController. Existing products:all behavior and its Redis-failure 500 remain unchanged until explicitly refactored.

1. Hazırlık

Mevcut projeden doğrulandı: Product cache is currently Redis String JSON for 10 minutes; Redis errors propagate to error middleware; Update/Delete do not invalidate. StackExchange.Redis, DbContext and singleton multiplexer already exist. No package/migration required.

Bu adımda sık yapılan hata: Blind Redis-to-SQL fallback under unbounded load. This example collapses requests per process and logs Redis errors; production also needs DB concurrency limit/circuit breaker.

2. Model ve veritabanı

Mevcut projeden doğrulandı: Existing Product entity already has Id/Name/Price. The cache is rebuildable; no entity, DbSet or migration is needed.

Bu adımda sık yapılan hata: Editing SQLite schema to store a disposable cache copy.

3. DTO’lar

Mevcut projeden doğrulandı: GET response can reuse the existing Product model shape from current endpoint. No new DTO is required for this read-only endpoint; do not expose internal fields if the model later changes.

Bu adımda sık yapılan hata: Returning Redis raw key/cache metadata to API consumers.

5. Servis katmanı

Dosya yolu: RestApi/Services/IProductCatalogCache.cs · Önerilen geliştirme

using System.Collections.Generic;
using System.Threading;
using System.Threading.Tasks;
using RestApi.Models;
namespace RestApi.Services;
public interface IProductCatalogCache
{
    Task<IReadOnlyList<Product>> GetAllAsync(CancellationToken ct);
}

Dosya yolu: RestApi/Services/ProductCatalogCache.cs · Önerilen geliştirme

using System;
using System.Collections.Generic;
using System.Linq;
using System.Text.Json;
using System.Threading;
using System.Threading.Tasks;
using Microsoft.EntityFrameworkCore;
using Microsoft.Extensions.Logging;
using RestApi.Data;
using RestApi.Models;
using StackExchange.Redis;
namespace RestApi.Services;
public sealed class ProductCatalogCache(
    ApplicationDbContext context, IConnectionMultiplexer multiplexer,
    ILogger<ProductCatalogCache> logger) : IProductCatalogCache
{
    private static readonly SemaphoreSlim RefreshGate = new(1, 1);
    private readonly IDatabase _redis = multiplexer.GetDatabase();

    public async Task<IReadOnlyList<Product>> GetAllAsync(CancellationToken ct)
    {
        var cacheAvailable = true;
        try
        {
            var cached = await _redis.StringGetAsync(ProductCacheKeys.All);
            if (!cached.IsNull)
            {
                var products = JsonSerializer.Deserialize<List<Product>>(cached.ToString());
                if (products is not null) return products;
            }
        }
        catch (RedisException ex)
        {
            cacheAvailable = false;
            logger.LogWarning(ex, "Redis read failed; loading product list from SQLite.");
        }
        catch (JsonException ex)
        {
            logger.LogWarning(ex, "Product cache payload is invalid; rebuilding from SQLite.");
            try { await _redis.KeyDeleteAsync(ProductCacheKeys.All); }
            catch (RedisException redisEx)
            {
                cacheAvailable = false;
                logger.LogWarning(redisEx, "Could not remove invalid product cache.");
            }
        }

        await RefreshGate.WaitAsync(ct);
        try
        {
            if (cacheAvailable)
            {
                try
                {
                    var secondRead = await _redis.StringGetAsync(ProductCacheKeys.All);
                    if (!secondRead.IsNull)
                    {
                        var second = JsonSerializer.Deserialize<List<Product>>(secondRead.ToString());
                        if (second is not null) return second;
                    }
                }
                catch (RedisException ex)
                {
                    cacheAvailable = false;
                    logger.LogWarning(ex, "Redis recheck failed; continuing with SQLite.");
                }
                catch (JsonException ex)
                {
                    logger.LogWarning(ex, "Redis recheck payload invalid; rebuilding from SQLite.");
                }
            }
            var rows = await context.Products.AsNoTracking().OrderBy(p => p.Id).ToListAsync(ct);
            if (cacheAvailable)
            {
                var ttl = TimeSpan.FromMinutes(10) + TimeSpan.FromSeconds(Random.Shared.Next(30, 91));
                try
                {
                    await _redis.StringSetAsync(ProductCacheKeys.All,
                        JsonSerializer.Serialize(rows), ttl);
                }
                catch (RedisException ex)
                {
                    logger.LogWarning(ex, "Redis cache write failed; returning SQLite result.");
                }
            }
            return rows;
        }
        finally { RefreshGate.Release(); }
    }
}

Fallback is explicit and only Redis failures are degraded; SQLite errors still surface. Gate is process-local, not cross-instance. TTL jitter spreads later expiry but not initial cold-start load; add stale-while-revalidate only if product freshness policy permits.

Bu adımda sık yapılan hata: Catching all exceptions and returning an empty success list. Only expected Redis/JSON cache failures are handled; database failures remain visible.

7. Controller

Dosya yolu: RestApi/Controllers/ResilientProductsController.cs · Önerilen geliştirme

using System.Security.Claims;
using Microsoft.AspNetCore.Authorization;
using Microsoft.AspNetCore.Mvc;
using RestApi.Services;
namespace RestApi.Controllers;
[ApiController]
[Route("api/cache/products")]
[Authorize(Roles = "Product")]
public sealed class ResilientProductsController(IProductCatalogCache cache) : ControllerBase
{
    [HttpGet]
    public async Task<IActionResult> Get(CancellationToken ct)
    {
        if (!int.TryParse(User.FindFirstValue(ClaimTypes.NameIdentifier), out var userId)
            || userId <= 0) return Unauthorized();
        return Ok(await cache.GetAllAsync(ct));
    }
}

GET 200; anonymous 401; authenticated account without Product role 403; SQLite failure goes to existing error middleware. The NameIdentifier guard verifies the existing JWT identity even though this global catalog is not user-scoped.

Bu adımda sık yapılan hata: Claim read without using it as ownership for user-specific data. This route is global read-only; user-specific caches must include owner ID.

F · Request flow, outcomes, risks

HTTP → ErrorHandlerMiddleware → GlobalMiddleware → Authentication → Authorization(Product) → ProductController.GetAll → Redis GET → hit response OR SQLite SELECT → Redis SET EX 600 → response
Success: cache hit avoids SQLite query; cache miss queries SQLite and fills Redis.
Failure: Redis GET throws; no controller fallback; middleware catches → 500 JSON with exception message. It does not fail-open to SQLite.
  • TTL synchronized expiry stampedes all API instances and loads SQLite.
  • Create invalidates before DB SaveChanges; concurrent miss can repopulate old values during gap. Update/Delete omit invalidation.
  • Redis outage fallback can overload SQLite; circuit breaker, bounded concurrent DB work, stale strategy.
  • 5s Connect/Sync timeout configuration may increase wait during unavailable Redis/load; ConnectTimeout applies connection establishment, SyncTimeout synchronous operations; actual async operation behavior should be measured.
  • Eviction/memory and restart return cold cache. SQLite remains authority; no outage masking without design.

Outcomes: cache-aside, invalidation order, stampede, jitter, failure policy, stale data bounds. Prerequisite none; next Module 12 tests measurable outcome.

Tasks / checklist

  1. Update invalidation plan for Create/Update/Delete.
    İpucuOnly invalidate after DB commit; handle post-commit invalidation failure.
  2. Test concurrent reads at TTL expiry.
    İpucuCount SQLite SELECTs per cache miss burst.
  3. Stop Redis and record actual status/body/latency.
    İpucuException bubbles through middleware into 500, no SQLite fallback in current code.
Kendini değerlendir

1) TTL current? 10 minutes fixed. 2) Update/Delete invalidate? No. 3) Create order? Delete cache before SaveChanges. 4) Redis down GetAll? Exception, middleware returns 500; not SQLite fallback. 5) Redis fallback always safe? No, DB overload possible.

Sık yapılan hatalar

  • Only invalidate on create → update/delete stale data.
  • Fallback every timeout straight to SQLite → outage cascade.
  • Fixed common TTL for hot keys → synchronized stampede; jitter/single-flight.
