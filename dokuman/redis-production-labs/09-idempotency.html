Idempotency

İstemci retry’larında tek mantıksal isteğin yan etkisini bir kez üretin; Redis key tek başına yeterli değildir.

Mevcut yazma endpoint’leri doğrulandı · idempotency altyapısı yok

A · Problem / B · Redis’in yeri

Client timeout görüp aynı POST’u tekrar gönderdiğinde ilk istek aslında DB’ye yazılmış olabilir. Duplicate Product/Note/User kaydı oluşabilir. Redis SET NX PX hızlı claim/in-progress lock ve tamamlanmış response cache’i sağlar; eşzamanlı sahipliği koordine eder. Fakat crash, key eviction, DB commit-before-cache ve key TTL sonrası tekrar işleme penceresi vardır. SQLite transaction/unique constraints kalıcı doğruluk kaynağıdır. Ödeme/sipariş akışı mevcut değil; ödeme için Redis tek başına hiçbir zaman finansal doğruluk garantisi değildir. SQLite çok instance concurrency sınırlıdır.

C · Redis features + key

SET NX PX: key yokken claim al, lease TTL.
Request hash: aynı key, farklı body ise 409.
State: in-progress/completed/failed; complete response tekrar oynatılır.
KeyTipTTL / scope
idempotency:{userId}:{key}String JSON or Hash: state, requestHash, response, statusRetry policy retention; per authenticated user + client key. userId claim-derived, key length/format bounded; critical record SQLite.

D · Endpoint’ler

Idempotency API/filters Önerilen geliştirme; hedefler mevcut rotadır. POST api/product ve POST api/note gerçek; POST api/auth/register mevcut. Username unique index DB son savunmasıdır. Product requires Product role; Note requires Note role; Register currently no class-level auth in AuthController.

Metot/URLİstek / sonuçRedis / SQLite

E · Uygulama adımları

  1. Require bounded Idempotency-Key and compute canonical request hash; key scope includes authenticated user/endpoint. For anonymous register, normalized username hash is sensitive; don't put raw email in Redis key.
  2. SET NX PX claim; if existing hash differs return 409; completed response replay; in-progress return 409/202 and retry hint.
  3. Commit DB mutation and idempotency record atomically where possible via SQLite transaction table. Redis-only record can disappear; reconcile incomplete leases.
  4. Store safe response only; omit password/token, large bodies, secrets. Expiry retention aligned to client retries.

Adım Adım .NET Uygulama Rehberi

Önerilen geliştirme: Idempotency middleware/service yok. Use SQLite transaction + unique idempotency row as durable authority; Redis caches completed safe responses only.

1. Hazırlık

Mevcut projeden doğrulandı: .NET 9, SQLite EF Core, StackExchange.Redis and singleton multiplexer available. No package needed.

Bu adımda sık yapılan hata: Redis SET NX result as transactional guarantee for a separate SQL write. Redis and SQLite cannot share one atomic transaction.

using System;
namespace RestApi.Services;
public static class IdempotencyRedisKeys
{
    public static string Response(int userId, string key) =>
        userId > 0 && !string.IsNullOrWhiteSpace(key)
            ? $"idempotency:user:{userId}:{key}"
            : throw new ArgumentException("Invalid idempotency key.");
}

Accept only an opaque, bounded header key matching ^[A-Za-z0-9_-]{1,120}$ before calling helper. Avoid raw PII in key.

using System.Threading;
using System.Threading.Tasks;
using RestApi.Models.Dto;
namespace RestApi.Services;
public interface IIdempotentProductService

    Task<(IdempotentProductResponseDto Response, bool Replayed)> CreateAsync(

}

Dosya yolu: RestApi/Services/IdempotentProductService.cs · Önerilen geliştirme

using System;
using System.Security.Cryptography;
using System.Text;
using System.Text.Json;
using System.Threading;
using System.Threading.Tasks;
using Microsoft.EntityFrameworkCore;
using Microsoft.Extensions.Logging;
using RestApi.Data;
using RestApi.Models;
using RestApi.Models.Dto;
using StackExchange.Redis;
namespace RestApi.Services;
public sealed class IdempotentProductService(
    ApplicationDbContext context, IConnectionMultiplexer multiplexer,
    ILogger<IdempotentProductService> logger) : IIdempotentProductService
{
    private readonly IDatabase _redis = multiplexer.GetDatabase();
    public async Task<(IdempotentProductResponseDto Response, bool Replayed)> CreateAsync(
        int userId, string key, IdempotentProductRequestDto request, CancellationToken ct)
    {
        var hash = Convert.ToHexString(SHA256.HashData(Encoding.UTF8.GetBytes(
            JsonSerializer.Serialize(new { request.Name, request.Price }))));
        var redisKey = (RedisKey)IdempotencyRedisKeys.Response(userId, key);
        try
        {
            var cached = await _redis.StringGetAsync(redisKey);
            if (!cached.IsNull)
            {
                var entry = JsonSerializer.Deserialize<CachedResponse>(cached.ToString());
                if (entry is not null && entry.Hash == hash)
                    return (entry.Response, true);
                if (entry is not null) throw new InvalidOperationException("Key reused with different request.");
            }
        }
        catch (RedisException ex) { logger.LogWarning(ex, "Idempotency cache unavailable; checking SQLite."); }

        var existing = await context.IdempotencyRecords.AsNoTracking()
            .SingleOrDefaultAsync(x => x.UserId == userId && x.Key == key, ct);
        if (existing is not null)
        {
            if (existing.RequestHash != hash)
                throw new InvalidOperationException("Key reused with different request.");
            var replay = JsonSerializer.Deserialize<IdempotentProductResponseDto>(existing.ResponseJson)
                ?? throw new InvalidOperationException("Stored idempotency response is invalid.");
            await CacheAsync(redisKey, new CachedResponse(hash, replay));
            return (replay, true);
        }

        await using var transaction = await context.Database.BeginTransactionAsync(ct);
        var product = new Product { Name = request.Name, Price = request.Price };
        context.Products.Add(product);
        await context.SaveChangesAsync(ct);
        var response = new IdempotentProductResponseDto(product.Id, product.Name, product.Price);
        context.IdempotencyRecords.Add(new IdempotencyRecord
        {
            UserId = userId, Key = key, RequestHash = hash,
            ResponseJson = JsonSerializer.Serialize(response), CreatedAtUtc = DateTime.UtcNow
        });
        await context.SaveChangesAsync(ct);
        await transaction.CommitAsync(ct);
        await CacheAsync(redisKey, new CachedResponse(hash, response));
        return (response, false);
    }

    private async Task CacheAsync(RedisKey key, CachedResponse value)
    {
        try { await _redis.StringSetAsync(key, JsonSerializer.Serialize(value), TimeSpan.FromHours(24)); }
        catch (RedisException ex) { logger.LogWarning(ex, "Idempotency response cache write failed."); }
    }
    private sealed record CachedResponse(string Hash, IdempotentProductResponseDto Response);
}

SQLite transaction commits product+idempotency row atomically. Redis is optional response cache; cache miss/outage consults SQLite. Concurrent first requests can race on the unique index: one succeeds, the other surfaces DB error; production should catch the unique violation and reload the completed row, or use a DB-specific claim protocol. Keep retention aligned with client retry window.

Bu adımda sık yapılan hata: Catching every DbUpdateException as replay. Only recognize the composite unique-key conflict and verify request hash before returning stored response.

7. Controller

Dosya yolu: RestApi/Controllers/IdempotentProductsController.cs · Önerilen geliştirme

using System.Security.Claims;
using System.Text.RegularExpressions;
using Microsoft.AspNetCore.Authorization;
using Microsoft.AspNetCore.Mvc;
using RestApi.Models.Dto;
using RestApi.Services;
namespace RestApi.Controllers;
[ApiController]
[Route("api/idempotent-products")]
[Authorize]
public sealed class IdempotentProductsController(IIdempotentProductService service)
    : ControllerBase
{
    [HttpPost]
    public async Task<IActionResult> Create(
        [FromHeader(Name = "Idempotency-Key")] string? key,
        IdempotentProductRequestDto request, CancellationToken ct)
    {
        if (!int.TryParse(User.FindFirstValue(ClaimTypes.NameIdentifier), out var userId)
            || userId <= 0) return Unauthorized();
        if (key is null || !Regex.IsMatch(key, "^[A-Za-z0-9_-]{1,120}$"))
            return BadRequest("A valid Idempotency-Key header is required.");
        try
        {
            var result = await service.CreateAsync(userId, key, request, ct);
            return result.Replayed ? Ok(result.Response) : StatusCode(201, result.Response);
        }
        catch (InvalidOperationException) { return Conflict(); }
    }
}

First request 201, identical replay 200 with original product response, same key/different body 409, missing/malformed key or invalid DTO 400, anonymous 401. No password or token is stored in replay body.

Bu adımda sık yapılan hata: Idempotency key alone as authorization. Controller remains authenticated and scopes database uniqueness by claim userId.

.NET example · proposed idempotency claim

using StackExchange.Redis;

public sealed class IdempotencyClaim(IConnectionMultiplexer mux)
{
    public async Task<bool> TryClaimAsync(
        int userId, string idempotencyKey, string requestHash)
    {
        var key = (RedisKey)$"idempotency:{userId}:{idempotencyKey}";
        var claimed = await mux.GetDatabase().StringSetAsync(
            key, $"in-progress:{requestHash}",
            TimeSpan.FromSeconds(30), When.NotExists);
if (!claimed)
{
    // Load existing state; reject a body-hash mismatch;
    // replay completed response or report in-progress.
}
        return claimed;
    }
}

F · Akış / risk / outputs

HTTP + Idempotency-Key → middleware/controller → Redis claim → SQLite transaction/write → store durable result → Redis completed response → replay
Success: first request claims, DB writes once, stores result; retries receive equivalent outcome.
Failure: DB commits, process crashes before Redis complete → retry must query durable idempotency row or duplicate remains possible.
  • Redis lock TTL expiry while original request still running can permit second processing.
  • Same key with different payload must 409; hash canonicalization carefully defined.
  • SQLite unique index is last line for registration. Register response currently includes returned User with Password null? Existing AuthController.Register DOES NOT null it: it hashes then returns user, so hash may leak; fix is recommendation.
  • Redis↔SQLite atomic transaction doesn’t exist; durable idempotency table/outbox and recovery required for critical operations.

Learn idempotency vs at-most-once, response replay, request hash, DB constraints. Prereq Module 08 retry/worker ideas; next Module 10 critical concurrency.

Tasks / checklist

    İpucuClaim plus stored response; DB write still needs recovery.

    İpucuCanonical JSON hash compare.

Kendini değerlendir

1) SET NX does it guarantee one durable DB write? No. 2) Key/body mismatch? 409. 3) crash after SQL? Durable record/reconciliation. 4) Register existing protection? Username unique index in migration.

Sık yapılan hatalar

  • Redis key ekleyip bitti sanmak → state machine/recovery/db constraint kur.
  • Request body’yi canonicalize etmeden compare etmek → stable hash scheme.
  • Şifre/token içeren response saklamak → response allowlist/sanitize.
